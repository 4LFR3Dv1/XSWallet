0. Objetivo do Sistema

Resolver o problema de controle de saldo por endereço (on-chain) e permitir integração segura e auditável entre depósitos on-chain, índice de UTXOs e payouts multi-rede.

  1. Depósitos/recebimentos rastreados pela blockchain (principalmente USDT na Liquid)
  2. Saldo por usuário derivado on-chain (UTXO por endereço), com reservas internas de UTXO
  3. Saques/payouts (BTC/Liquid) com idempotência, retry e DLQ
  4. Integração nativa com o fluxo do app DominiPay (PIX/Depix)
Nota realista: o saldo é derivado da própria blockchain (UTXOs por endereço) e das reservas internas de UTXO (lock/hold). Não usamos ledger de crédito/débito no MVP; se necessário para contabilidade, pode ser adicionado sem alterar a fonte de verdade on-chain.

1. Sumário Executivo

DomniWallet Wallet + Payout Service é um sistema custodial por API que controla saldo por usuário a partir do índice on-chain de UTXOs (por endereço) e depósitos on-chain (principalmente USDT na Liquid), além de executar payouts multi-rede (BTC e L-BTC). Lightning fica fora do MVP atual. DominiPay integra PIX/Depix e consulta saldo/saques via Wallet API.

1.1 Modelo de Operação (Custodial + Treasury Payout)

Modelo Custodial: BTC usa derivação da master seed (BIP86/P2TR). Liquid gera endereços diretamente no elementsd (wallet do node). O cliente não controla a seed; a DomniWallet custodia fundos e opera um índice on-chain de UTXOs + reservas internas para saques.
Aspecto Descrição
Custódia de Clientes SIM — chave do serviço sob custódia do Wallet Service (vault/HSM); seed de recuperação do usuário é entregue uma única vez e não armazenada
Tesouraria Carteiras operadas pela empresa para payouts
Fluxo Depósitos confirmados → indexação de UTXOs → saques/payouts
Risco Empresa assume risco de custódia e liquidez; cliente assume risco de endereço/invoice
Tabela 1.1: Modelo de Operação

Gatilho de Payout (Depix)

Decisão operacional (v1): o saldo spendable é liberado após depix_confs=2. No Modelo A, o gateway Depix deposita direto no endereço do usuário e o Watcher indexa o UTXO. No Modelo B (híbrido), DominiPay enviaria depix_confirmed para o Wallet Service, mas este modelo requer ledger interno e fica fora do MVP on-chain. Payouts só são criados com saldo disponível (UTXOs não reservados).

Fluxo atual: PIX recebido → Depix enviado → UTXO confirmado (Modelo A) → POST /v1/withdrawals → Wallet Service chama Payout Service.

2.4 Custódia e Derivação de Chaves

O Wallet Service é custodial para operações do dia a dia. Para BTC, usa P2TR com dois caminhos: key-path (chave do serviço) para saques normais e script-path de recuperação do usuário com CSV por tier de risco. Cada usuário recebe um account_index determinístico (hardened) para o key-path BIP86. O sistema gera uma seed de recuperação para o usuário, entrega uma única vez e não armazena; apenas o pubkey/xpub é guardado para compor o script de recuperação. Para Liquid, os endereços são gerados diretamente no elementsd (wallet do node), associados ao account_id por label.

Item Decisão
Conta por usuário accounts(uuid → account_index) determinístico
BTC (custódia) P2TR key-path (serviço): m/86'/0'/account'/0/i
BTC (recuperação) Script-path com CSV por tier de risco; pubkey do usuário derivado de seed gerada e entregue uma única vez
Seed do usuário Gerada pelo sistema, entregue uma única vez e não armazenada; guardar apenas pubkey/xpub
Liquid Endereços gerados no elementsd (wallet do node); label por account_id
Tron BIP44 (coin type 195): m/44'/195'/account'/0/i (custodial)
UUID ≠ PubKey Não usar uuid como pubkey (mistura identidade com criptografia)
Tabela 2.3: Modelo de Custódia e Derivação

2.4.1 Recuperação (Break-glass) BTC

O caminho de recuperação do usuário usa script-path com CSV por tier de risco. O sistema gera a seed de recuperação e entrega uma única vez; não armazena a seed. Apenas o user_xpub (por conta) é guardado para compor o script. A recuperação exige reconstruir o descriptor P2TR (key-path do serviço + script-path CSV com pubkey do usuário) e varrer os UTXOs após o timelock.

  • Padrão recomendado: user_xpub por conta (não pubkey única) para permitir recuperação por endereço e rotação segura.
  • Compatibilidade: a recuperação deve usar wallet que aceite descriptors P2TR com CSV (ou fluxo de sweep custom).
  • UX de recuperação: fornecer ao usuário o user_xpub, policy de CSV e exemplo de derivação m/86'/0'/account'/0/i para reconstrução.
Segurança mínima: seed do serviço armazenada em vault/TPM/HSM (ou encrypted-at-rest + unlock controlado). A seed de recuperação do usuário é entregue uma única vez e não é armazenada (guardar apenas pubkey/xpub). Hot wallets com limites e política de backup/rotação.

2.6 Watcher / Indexer (Observação de Depósitos)

Como observar endereços na prática:

  • Opção 1 (rápida, MVP): usar wallet RPC dos nodes; importar descriptors e listar transações. Prós: rápida; Contras: depende de indexing e rescan.
  • Opção 2 (robusta): indexador próprio + mempool/esplora. Prós: escala melhor; Contras: mais trabalho.
Recomendação: iniciar com Opção 1 + reconciliação periódica. Evoluir para Opção 2 quando throughput justificar.
Robustez do watcher: tratar reorgs, UTXO que some, transações RBF substituídas e confirmações revertidas (confirmed → mempool). Persistir block_hash e height por UTXO e ter reconciliação periódica para corrigir o estado. Para redes account-based (Tron), persistir saldo + último bloco e reconciliar transferências de token.

func ValidateBTCAddress(addr string) error {
    // 1. Verificar mixed-case (BIP-173)
    if hasMixedCase(addr) && strings.HasPrefix(strings.ToLower(addr), "bc1") {
        return ErrMixedCaseBech32
    }
    // 2. Chamar bitcoind validateaddress
    resp, _ := rpc.Call("validateaddress", addr)
    if !resp.IsValid {
        return ErrInvalidAddress
    }
    return nil
}

5.2.2 Lightning Invoice (Futuro)

func ValidateLNInvoice(invoice string, expectedAmount int64) error {
    decoded, err := lnd.DecodePayReq(invoice)
    if err != nil {
        return ErrInvalidInvoice
    }
    
    // Expiração
    expiresAt := decoded.Timestamp + decoded.Expiry
    if time.Now().Unix() > expiresAt {
        return ErrInvoiceExpired
    }
    
    // 80% do expiry
    remaining := expiresAt - time.Now().Unix()
    if remaining < int64(decoded.Expiry)*0.2 {
        return ErrInvoiceNearExpiry
    }
    
    // Amount
    if decoded.NumSatoshis == 0 {
        // Zero-amount: aceitar se expectedAmount > 0
    } else if decoded.NumSatoshis != expectedAmount {
        return ErrAmountMismatch
    }
    
    return nil
}

6. Fluxos de Execução

6.1 Fluxos Integrados (Wallet + UTXO Index)

6.1.1 Onboarding (conta + endereço)

  1. DominiPay cria usuário e chama POST /v1/accounts com uuid
  2. DominiPay solicita endereços por rede/asset (ex.: Liquid USDT, Liquid L-BTC)
  3. Wallet Service deriva e retorna o endereço, gravando em addresses

6.1.2 Depósito normal (USDT Liquid)

  1. Cliente deposita USDT na Liquid no endereço do usuário
  2. Watcher detecta UTXO (txid:vout, asset_id, amount, address)
  3. Após confirmations >= N, grava em chain_utxos
  4. Saldo é derivado de chain_utxos (menos UTXOs reservados)
  5. DominiPay consulta saldo via GET /v1/accounts/{uuid}/balances

6.1.2b Depósito normal (USDC Tron)

  1. Cliente deposita USDC (TRC20) no endereço Tron do usuário
  2. Watcher detecta transferência (txid, contract, amount, address)
  3. Após confirmations >= N, grava em chain_accounts
  4. Saldo é derivado de chain_accounts (menos reservas)
  5. DominiPay consulta saldo via GET /v1/accounts/{uuid}/balances

6.1.3 Fluxo PIX → Depix → Crédito

Evolução futura (ledger): se for necessário saldo lógico (Modelo B), definir eventos geradores (depix_confirmed, swap_fill, estorno) e um reconciliador que concilia ledger vs on-chain sem quebrar a fonte de verdade.

Dois modelos possíveis, dependentes do gateway Depix:

Modelo A (suportado no MVP): Depix deposita direto no endereço do usuário.
PIX confirmado → Depix envia para endereço USDT do usuário → Watcher indexa UTXO automaticamente.
Modelo B (híbrido): Depix deposita na tesouraria.
PIX confirmado → DominiPay emite evento depix_confirmed → este modelo exige ledger interno e fica fora do escopo do MVP on-chain.

6.1.4 Payout (saque) BTC/Liquid/Tron

  1. DominiPay chama POST /v1/withdrawals com rede, asset, amount e destination
  2. Wallet Service valida saldo on-chain e destino; reserva UTXOs (lockunspent) ou saldo lógico (Tron)
  3. Wallet Service chama Payout Service com idempotência
  4. Payout Service executa (BTC/Liquid/Tron) e monitora confirmações
  5. Ao concluir: marcar UTXOs como spent e status COMPLETED
  6. Se falhar: liberar reservas/locks

7. Resiliência

7.1 Circuit Breaker

Circuit breakers são independentes por rede. BTC aberto NÃO bloqueia Liquid.

type CircuitBreaker struct {
    State            string        // CLOSED, OPEN, HALF_OPEN
    FailureCount     int
    FailureThreshold int           // default: 5
    OpenDuration     time.Duration // default: 60s
    LastFailure      time.Time
    Queue            []PayoutRequest // Fila preservada
    MaxQueueSize     int             // default: 100 (backlog limit)
}

func (cb *CircuitBreaker) Execute(fn func() error) error {
    if cb.State == "OPEN" {
        if time.Since(cb.LastFailure) > cb.OpenDuration {
            cb.State = "HALF_OPEN"
        } else {
            // Shed load se backlog exceder limite
            if len(cb.Queue) >= cb.MaxQueueSize {
                return ErrBacklogFull // Retryable, não enfileira
            }
            return ErrCircuitOpen // Enqueue
        }
    }
    
    err := fn()
    if err != nil {
        cb.FailureCount++
        cb.LastFailure = time.Now()
        if cb.FailureCount >= cb.FailureThreshold {
            cb.State = "OPEN"
        }
        return err
    }
    
    cb.FailureCount = 0
    cb.State = "CLOSED"
    return nil
}
Listagem 7.1: Circuit Breaker com Backlog Limit
Proteção Financeira: Quando circuit abre, payouts são enfileirados até o limite. Se len(queue) >= MaxQueueSize, novos payouts são rejeitados com ErrBacklogFull (retryable). Isso evita "fila de dívida" em burst de Depix.
Parâmetro Valor Padrão Descrição
MaxQueueSize 100 por rede Limite de backlog; acima disso, shed load
FailureThreshold 5 Falhas consecutivas para abrir circuit
OpenDuration 60s Tempo em OPEN antes de tentar HALF_OPEN

9. Runbook Operacional

9.1 RBF - Replace-By-Fee

Para transações BTC stuck no mempool por mais de 1 hora:

# 1. Verificar status da tx
bitcoin-cli gettransaction <txid>

# 2. Calcular novo fee (target: próximo bloco)
NEW_FEE=$(bitcoin-cli estimatesmartfee 2 | jq '.feerate')

# 3. Bump fee
bitcoin-cli bumpfee <txid> '{"fee_rate": '$NEW_FEE'}'

# 4. Verificar nova tx
bitcoin-cli gettransaction <new_txid>
