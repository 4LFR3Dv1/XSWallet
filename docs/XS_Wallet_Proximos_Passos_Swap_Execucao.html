Escopo Execução real após locked, assinatura MuSig2 e transições até broadcast/provider

1. Sumário Executivo

Este documento detalha como implementar os próximos passos do pipeline de swaps para sair do estado parcial atual (lock concluído, execução final pendente) e chegar ao fluxo operacional de execução real para chain e reverse, com assinatura MuSig2, reconciliação idempotente e visibilidade completa por eventos.

O plano está alinhado com a especificação e com o código existente, incluindo a evolução já entregue no serviço gRPC de swap events/streams.

Bloco Status atual Próximo alvo
Streaming de swaps Concluído Hardening de latência/backpressure
Chain/Reverse create + lock Concluído Hardening operacional e cobertura E2E sem simulação
MuSig2 partial signing Concluído Fechar executor de claim/refund final para todos os caminhos
Watcher de execução Parcial Consolidar evidência on-chain de refund multi-chain e path final de fallback

2. Baseline Atual do Código

2.1 Itens já disponíveis

  • swap_events persistidos e usados no streaming do SwapService.
  • GetSwapEvents, WatchSwap e WatchAllSwaps implementados com incremento por seq.
  • Integrações reais com Boltz testnet para criação de chain e reverse com validação de schema.
  • Persistência de locked_intent e boltz_raw no fluxo de criação.

2.2 Lacunas que impedem execução completa

  • Evidência objetiva de refund ainda precisa ser expandida além de BTC (ex.: Liquid/LN quando aplicável).
  • Fallback script-path ainda exige fechamento de execução final completa (claim/refund) em todos os cenários.
  • Watcher já valida status autoritativo, mas falta hardening de backpressure/latência para produção contínua.
  • Frontend precisa finalizar histórico/eventos em tempo real por stream nativo (hoje base incremental por polling).
Invariante de segurança: eventos WebSocket do provider são apenas trigger. Toda ação crítica precisa de validação por fonte autoritativa (status API + confirmação chain/LN), conforme especificação técnica v2.

3. Máquina de Estados Alvo para Execução

Sequência alvo principal (chain):

stateDiagram-v2 [*] --> waiting_claim_details waiting_claim_details --> signing_musig2_partial: start_signing signing_musig2_partial --> sent_partial_to_provider: send_partial sent_partial_to_provider --> waiting_provider_broadcast: await_broadcast waiting_provider_broadcast --> completed: claim_confirmed waiting_provider_broadcast --> fallback_script_ready: coop_failed fallback_script_ready --> refunding: timeout_or_manual refunding --> failed: refund_error

Fluxo de execução cooperativa/fallback para chain, alinhado ao spec.

signing_musig2_partial start_signing Gerar partial signature Nonce/session válidos e sem reuso

4. Implementação Detalhada por Camada

4.1 Persistência (DB + locked_intent)

Objetivo

Persistir dados suficientes para reexecutar assinatura/claim/refund após restart sem depender de memória de processo.

Campos mínimos obrigatórios no locked_intent

  • boltz_id, preimage_hash, swap_kind.
  • lockup_details: lockupAddress, timeoutBlockHeight, serverPublicKey, swapTree.
  • claim_details: lockupAddress, timeoutBlockHeight, blindingKey, serverPublicKey, swapTree.
  • musig (bloco reservado): sessão, nonce pública local, nonce agregada, estado da assinatura.

Arquivos foco

  • core/internal/swap/chain.go
  • core/internal/swap/reverse.go
  • core/internal/db/db.go

4.2 MuSig2 (assinatura parcial real)

Objetivo

Trocar placeholders/mocks por fluxo real de assinatura com chave derivada do vault, nonce segura e sessão reidratável.

Requisitos técnicos

  • Derivação de chave por swap_key_index com domínio de derivação dedicado.
  • Geração de nonce única por sessão; proibição explícita de reuso.
  • Persistência de identificador de sessão e material necessário para retomar assinatura sem reuso indevido.
  • Zero vazamento de secnonce em logs, eventos ou erros serializados.

Arquivos foco

  • core/internal/musig2/session.go
  • core/internal/vault/derivation.go
  • core/internal/swap/engine.go
Risco crítico: reuso de nonce em MuSig2 compromete a chave privada. O fluxo deve falhar de forma segura se detectar sessão inconsistente/repetida.

4.3 Provider/Boltz (execução cooperativa)

Objetivo

Garantir contrato de requisição/resposta real para envio de partials e leitura de status de execução.

Ações

  • Formalizar structs de request/response para endpoints de coop signing e status.
  • Persistir payload bruto de resposta em boltz_raw para auditoria e debug forense.
  • Normalizar códigos/erros transientes vs terminais para estratégia de retry.

Arquivos foco

  • core/internal/boltz/boltz.go
  • core/internal/boltz/types.go
  • core/internal/provider/provider.go

4.4 Watcher/Reconcile (orquestração idempotente)

Objetivo

Executar transições automáticas de forma segura, idempotente e recuperável após falha/restart.

Ações

  • Mapear status normalizado do provider para triggers de transição no engine.
  • Aplicar CAS por versão em toda transição sensível.
  • Registrar em swap_events cada tentativa/sucesso/erro com trigger e detalhes úteis.
  • Backoff exponencial com teto + jitter para polling de status.

Arquivos foco

  • core/internal/watcher/watcher.go
  • core/internal/swap/engine.go

6. Plano de Entrega em Fases

6.1 Fase A - Persistência e contratos (curta)

  1. Concluir formato versionado de locked_intent para chain/reverse.
  2. Ajustar provider types para dados reais de execução cooperativa.
  3. Adicionar testes unitários de serialização/compatibilidade.

6.2 Fase B - MuSig2 real

  1. Implementar sessão real (derivação de chave + nonce + partial).
  2. Persistir sessão e bloquear reuso de nonce por desenho.
  3. Criar testes de regressão com falhas esperadas de sessão inválida.

6.3 Fase C - Watcher execução chain

  1. Ligar gatilhos do provider aos estados de execução chain.
  2. Avançar até waiting_provider_broadcast com idempotência.
  3. Cobrir restart/replay no meio da execução.

6.4 Fase D - Reverse integração equivalente

  1. Teste de integração real para schema reverse.
  2. Persistência equivalente no intent e eventos.
  3. Harmonizar caminhos comuns chain/reverse no executor.

7.2 Cenários obrigatórios de robustez

  • Restart de processo entre signing_musig2_partial e sent_partial_to_provider.
  • Erro 5xx temporário do provider durante envio de partial.
  • Evento WS duplicado fora de ordem.
  • Timeout de espera para broadcast cooperativo (entrada em fallback).

7.3 Métricas de sucesso

  • 0 transições inválidas em swap_events (monotonicidade por swap).
  • 0 reuso de nonce detectado em suíte de testes + runtime guardrails.
  • Fluxo chain testnet repetível em execuções consecutivas com ids distintos.
  • Tempo médio até waiting_provider_broadcast dentro da janela operacional esperada.

8. Ajustes Necessários de Frontend

8.1 Estados que a UI deve suportar explicitamente

  • waiting_claim_details
  • signing_musig2_partial

8.2 Ações práticas

  • Remover mensagens genéricas e expor erro técnico normalizado com contexto da transição.
  • Atualizar Swap History para refletir estados intermediários e não apenas finalizados.
  • Evoluir consumo de eventos para stream nativo no frontend (além do incremental atual).

9. Riscos e Mitigações

Risco Impacto Mitigação
Reuso de nonce MuSig2 Comprometimento criptográfico Persistência de sessão + trava de unicidade + fail-fast
Divergência status local x provider Transição incorreta WS apenas trigger; validar status autoritativo antes de transição
Quebra por schema novo do provider Falha de execução em runtime Integração contínua testnet + boltz_raw persistido para diagnóstico
UI desatualizada de estados Operação cega e suporte difícil Atualizar mapeamento de estados + timeline de eventos

10. Definition of Done (DoD)

  1. Chain e reverse executam até estado terminal com validação objetiva de evidência (claim/refund) sem simulação.
  2. Refund script-path executa broadcast real e persistência completa de artefatos em todos os cenários suportados.
  3. Reconcile é idempotente sob restart, sem duplicar operações nem quebrar versão CAS.
  4. swap_events registra integralmente o caminho de execução; streams refletem o mesmo histórico.
  5. Frontend exibe estados/eventos em paridade com backend usando stream nativo e histórico completo.
Próxima ação recomendada: fechar evidência on-chain de refund multi-chain e execução final de fallback script-path, para sair de "parcial avançado" para "fluxo completo".
