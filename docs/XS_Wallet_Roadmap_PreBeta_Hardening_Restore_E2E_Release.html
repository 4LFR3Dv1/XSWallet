XS WALLET

Roadmap Pré-Beta: Hardening, Restore UI, E2E e Release Pipeline
Documento Plano de Evolução Pré-Beta
Versão 1.0.0
Projeto XS Wallet v0.2.x
Data 19 Fevereiro 2026
Escopo Segurança, fluxo de restauração, qualidade E2E e pipeline de release

1. Objetivo

Concluir os blocos críticos para elevar o XS Wallet do estágio de MVP avançado para pré-beta técnico, com foco em segurança operacional, completude de fluxo de usuário e confiabilidade de entrega.

2. Escopo Macro

  1. Hardening final de segurança.
  2. Restore completo na UI (importação de carteira).
  3. Suíte E2E ampla e estável.
  4. Pipeline final de release com gates objetivos.

3. Fase 1 - Hardening Final de Segurança

3.1 Gestão de segredos e configuração

  • Remover placeholders e defaults inseguros de produção.
  • Padronizar .env por ambiente (dev/stage/prod).
  • Validar boot com fail-fast quando variável obrigatória faltar.
  • Documentar matriz de env vars no docs.

3.2 Sessão e autenticação

  • Garantir uso exclusivo de session_id real após unlock.
  • Invalidar sessão no lock/logout e em not_unlocked.
  • Padronizar resposta de erro Unauthenticated para UI.
  • Adicionar testes de expiração e sessão inválida.

3.3 IPC, bridge e superfície de ataque

  • Revisar whitelist de canais IPC e payload validators.
  • Remover qualquer fallback que simule sucesso sem backend.
  • Aplicar timeout e rate-limit consistentes por operação mutável.
  • Revisar CSP/CORS e headers de segurança.
Risco principal: sessões inválidas causando comportamento inconsistente entre UI e backend. Mitigação: contrato explícito de estado + testes de regressão de autenticação.

4. Fase 2 - Restore Completo na UI

4.1 Fluxo funcional esperado

  1. Usuário escolhe Restore Wallet.
  2. Informa mnemonic (12/24 palavras) com validação local de formato.
  3. Define e confirma PIN (regras de segurança).
  4. Frontend chama endpoint de restore/import no backend.
  5. Em sucesso: segue para unlock/dashboard conforme estado retornado.

4.2 Requisitos técnicos

  • Estados explícitos de loading, erro e sucesso.
  • Mensagens de erro orientadas por causa real (mnemonic inválido, já existe wallet, etc.).
  • Proteção de rota para evitar dead-end e loops de navegação.
  • Paridade entre fluxo IPC e fallback HTTP.

4.3 Critérios de aceite do restore

  • Sem telas “coming soon” em caminho crítico.
  • Restore completo sem intervenção manual externa.
  • Session token válido após fluxo finalizado.

5. Fase 3 - Suíte E2E Ampla

5.1 Matriz mínima de cenários

Categoria Cenário Resultado esperado
Onboarding Primeira execução -> Create Wallet Vault inicializado, mnemonic exibido, unlock funcional
Restore Import por mnemonic válido Wallet restaurada e sessão coerente
Auth Token expirado/inválido Redireciono seguro para unlock + mensagem clara
Wallet Gerar endereço / visualizar histórico Sem duplicação, dados consistentes por chain
Network Status de serviços mainnet/regtest exibido corretamente

5.2 Estratégia de execução

  • Camada de smoke em cada PR crítico.
  • Suite full em pipeline principal.
  • Coleta de artefatos: logs, traces e screenshots.

6. Fase 4 - Pipeline Final de Release

6.1 Pipeline alvo

lint -> unit -> build -> e2e-smoke -> e2e-full -> package -> sign -> release

6.2 Gates obrigatórios

  • Build Electron/Frontend 100% verde.
  • E2E crítico sem falhas intermitentes abertas.
  • Checklist de segurança concluído.
  • Versão/tag e release notes geradas.

6.3 Entregáveis de release

  • Artefatos assinados por plataforma.
  • Notas de versão com breaking changes.
  • Plano de rollback documentado.

7. Sequência Recomendada de Implementação

  1. Hardening (segredos/sessão/IPC).
  2. Restore UI completo.
  3. E2E crítico e regressão de auth.
  4. Pipeline de release e empacotamento final.
Definição de pronto (pré-beta): fluxo completo de create/restore/unlock estável, segurança operacional validada, E2E crítico automatizado e pipeline de release reproduzível.
