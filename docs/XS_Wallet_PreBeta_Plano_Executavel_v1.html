2. Fase 1 - Hardening Final de Segurança

2.1 Gestão de segredos e configuração

Entregáveis

  • env.schema.ts (ou config.ts) com validação forte.
  • .env.example, .env.dev, .env.stage, .env.prod (ou documentação equivalente).
  • Fail-fast no boot quando env obrigatória faltar.

Contrato mínimo

  • NODE_ENV in {development, staging, production}
  • BRIDGE_PORT, XSCORE_URL, SESSION_TTL_SECONDS, ALLOW_HTTP_FALLBACK, IPC_ENABLED, LOG_LEVEL
  • prod: ALLOW_HTTP_FALLBACK=false
  • prod: placeholders inseguros bloqueiam boot.

Checklist

  • [ ] Remover TODO, placeholder, defaultPin, testSession, mockSuccess.
  • [ ] Substituir por config validado com erro explícito.

2.2 Sessão e autenticação

Contrato

  • unlock(pin) retorna session_id real.
  • Frontend mantém sessão em memória (não persistir token sensível em localStorage).
  • Operações mutáveis exigem sessão válida.
  • lock/logout invalida sessão backend + limpa sessão frontend.
  • 401/Unauthenticated redireciona para /unlock com mensagem padrão.

Regra de consistência

  • status=unlocked só vale com sessão válida.
  • unlocked + session inválida deve ser tratado como locked.

Testes mínimos

  • [ ] unlock cria sessão e chamada protegida funciona.
  • [ ] lock invalida sessão e protege rotas/calls.
  • [ ] expiração de sessão dispara fallback seguro para unlock.

2.3 IPC, bridge e superfície de ataque

  • Whitelist fechada de canais IPC.
  • Schema de payload e de retorno por canal.
  • Timeout por operação e rate-limit em mutações.
  • Remover fallback que simula sucesso.
  • CSP/CORS/headers restritos ao necessário.

Deliverable técnico

  • [ ] ipcChannels.ts com contratos.
  • [ ] ipcRouter.ts com validação central.
  • [ ] security.md com canais/payloads/timeouts/limits.
Risco raiz: divergência de estado entre UI e backend por sessão inválida. Mitigação: contrato único de sessão + regressão automatizada de auth.

3. Fase 2 - Restore Completo na UI

3.1 Fluxo canônico

  1. /onboarding -> Restore Wallet.
  2. Entrada de mnemonic (12/24 palavras) + validação local (e BIP39 quando disponível).
  3. PIN + confirmação (>= 8).
  4. restoreVault({ mnemonic, pin }).
  5. Sucesso: segue para dashboard ou unlock conforme estado retornado.

3.2 Estados de UI obrigatórios

  • idle
  • validating
  • submitting
  • success
  • error com code, message e hint

3.3 Mapa de erros

  • MNEMONIC_INVALID -> "Mnemonic inválido. Verifique palavras e ordem."
  • VAULT_ALREADY_EXISTS -> "Já existe wallet local."
  • WEAK_PIN -> "PIN fraco. Use pelo menos 8 caracteres."
  • UNAVAILABLE -> "Indisponível nesta versão."

3.4 Gates

  • [ ] Restore completo sem intervenção externa.
  • [ ] Nenhum dead-end com "coming soon" em caminho crítico.
  • [ ] Paridade IPC vs HTTP comprovada.
  • [ ] Sessão coerente após restore.

4. Fase 3 - Suíte E2E Ampla

4.1 Estrutura

  • Smoke E2E: PRs críticos.
  • Full E2E: main/release.

4.2 Matriz mínima

CategoriaCenárioResultado esperado
OnboardingCreate wallet + confirm mnemonicSetup completo sem erro
RestoreMnemonic válido e inválidoSucesso e erro mapeado
AuthToken expirado/inválidoRedirect seguro para unlock
WalletGerar endereço por chainSem duplicação indevida
NetworkServiço offlineEstado degraded sem crash
ResiliênciaReiniciar bridge em runtimeUI estável com retry/erro seguro

4.3 Como rodar (template)

# smoke
npm run e2e:smoke

# full
npm run e2e:full

4.4 Artefatos obrigatórios

  • Logs bridge/electron/frontend.
  • Screenshots em falha.
  • Trace temporal dos passos.

5. Fase 4 - Pipeline Final de Release

5.1 Pipeline alvo

lint -> unit -> build -> e2e-smoke -> e2e-full -> package -> sign -> release

5.2 Gates obrigatórios

  • [ ] Build frontend/electron verde.
  • [ ] Smoke E2E sem falhas.
  • [ ] Full E2E sem flake aberto (ou quarantine formalizado).
  • [ ] Checklist de segurança concluído.
  • [ ] Versão/tag e release notes geradas.
  • [ ] Plano de rollback disponível.

5.3 Artefatos

  • Pacotes por plataforma suportada.
  • Assinatura/notarização quando aplicável.
  • Checksums publicados.

5.4 Rollback mínimo

  • Disponibilizar N-1.
  • Instrução de rollback nas release notes.
  • Compatibilidade de storage/migração documentada.

6. Sequência Prática (7 PRs)

  1. PR-01 Config hardening: schema env + fail-fast + docs.
  2. PR-02 Session contract: ciclo completo session_id + 401 handling.
  3. PR-03 IPC hardening: whitelist + validators + timeout/rate-limit.
  4. PR-04 Restore UI: fluxo completo + error map + roteamento.
  5. PR-05 E2E smoke: create/unlock/restore/auth invalid.
  6. PR-06 E2E full: regressão + resiliência + artefatos.
  7. PR-07 Release pipeline: package/sign/release + gates finais.

7. Definition of Done (Pré-Beta)

  • Create/Restore/Unlock estáveis ponta a ponta.
  • Sem divergência UI vs backend para sessão/401/lock/logout.
  • IPC/fallback auditáveis e previsíveis.
  • Smoke E2E em PR crítico e Full E2E em main.
  • Pipeline de release reproduzível com artefatos e rollback.
Status alvo: base pré-beta consistente para avançar em hardening operacional e release controlado.
